# 運用フェーズ — 設計凍結の契約

**設計は凍結した。ここから先はコードを書くフェーズではなく、
Discovery → CHEAP_TEST → Adopt → Publish → Revenue を回してデータを作るフェーズ。**

このドキュメントは「何をしてよくて、何をしてはいけないか」を固定するための契約書。
迷ったらここを読む。設計の経緯は [RESEARCH_SYSTEM.md](RESEARCH_SYSTEM.md)。

---

## 1. アルゴリズムを触ってよい条件（3つだけ）

| # | 再開条件 | 何を見るか |
|---|---|---|
| 1 | **初売上が出た** | 配点を変える前に「初売上の振り返り」で事実を記録し、再現性を確認する |
| 2 | **Adopt / Test 合計20件で売上0** | 探索・換金経路・案件選定のどこが間違っているかを校正表で見る |
| 3 | **5件診断で同じ運用異常が2回連続した** | **実装バグ・運用障害だけを直す。アルゴリズムは触らない** |

条件1〜3のいずれも満たしていないあいだは、**アルゴリズムを触らない。**
「もっと良い設計を思いついた」は再開条件ではない。

---

## 2. 20件未満でも直してよいもの（実装バグ・運用障害）

これらは配点の話ではなく、パイプラインが壊れている話。見つけたら直す。

- 明確な実装バグ
- 採用しても公開されない（`publish_zero` / `publish_low`）
- metrics が取れない（`metrics_missing`）
- 状態遷移がおかしい（`transition_stuck`）
- 人間の明示指示が無視される（`/adopt` が OBSERVE に落ちる、など）
- 同じ運用障害が2回連続する

## 2.5 認証情報の扱い

Claude Code はログインID・パスワード・銀行情報・API シークレットそのものを
要求しない。貼られても使わず、変更を促す。Secrets が必要なときは値ではなく
**Secret 名だけ**を指示する。オーナーから受け取るのはプログラム名・審査状況・
広告リンクURL・Secret 名まで。

## 3. 20件未満では原則触らないもの（アルゴリズム）

これらは**実績データが無いと正しく直せない**。異常を検出しても記録するだけにする。

| 触らないもの | 理由 |
|---|---|
| 100点の配点 | 実績との相関が取れていない |
| observed → 点数の mapping | `mapping_version` を記録して待つ |
| `scale_gate`（CV 2件 / 売上2回） | 仮値。実際の CV 分布を見てから |
| speculative しきい値（機会30 / 確信0.45） | `SPECULATIVE_RULE_VERSION` を記録して待つ |
| `opportunity` の計算式（√(D×B)） | 構造の妥当性は実績でしか検証できない |
| monetization の重み（1.0 / 0.6 / 0.2） | observed と inferred を分けて記録中 |
| percentile 化 / 回帰 / 機械学習 | サンプル数が足りない |

診断レビューはこの区別を出力に明記する。`**記録のみ（アルゴリズムは20件まで触らない）**`
の下に並んだ項目は、読んでも直さない。

## 4. 毎日・毎週やること

| いつ | 何が届く | やること | 所要 |
|---|---|---|---|
| 平日 05:00 JST | リサーチ結果 Issue | `/test <id>` を1つ押す（確信が低ければこれ） | 3〜5分 |
| 平日 06:00 JST | 承認 Issue | `/approve <id>` または `/approve all` | 3〜5分 |
| 月曜 08:00 JST | 実績入力リマインダー | `/m <niche> <累計views> <累計revenue>` | 30秒 |
| 火曜 07:00 JST | 週次レポート | 読むだけ。異常が出ていたら §2 の範囲で直す | 1分 |

**入力しなくても止まらない。** views が未入力なら Stage 0（判定不能）として記録され、
パイプラインは動き続ける。完璧な台帳より続く台帳を優先している。

## 5. 初売上が出たときの手順

**すぐ配点を変えない。** 週次レポートに「初売上の振り返り」が自動で出るので、
まず次の5点を記録する。

1. 何が売れたか
2. どの Stage を通ったか（Stage 遷移の履歴）
3. 探索候補（speculative）か通常候補か
4. 採用時の投資レベルと換金の根拠（observed / inferred）
5. 何本公開して到達したか

そのうえで**同じ構成でもう1件出せるか**を見る。再現できたら
`scale_gate` の閾値と配点の議論を始めてよい。1件では偶然と区別できない。

---

## 6. 20件で0円だったときの手順

`python -m src.pipeline calibrate` で予測 vs 実績の対応表を出す。見る順番はこれ。

1. **公開到達率** — 採用しても公開できていないなら、探索の問題ではない
2. **Stage 分布** — Stage 1 に偏っているならニッチ選定か制作、Stage 4 に偏っているなら案件
3. **`monetization_source`** — `inferred` ばかり売れていないなら、
   「LLM が稼げると言った」を信じすぎている。`AFF_*` を増やす方が先
4. **speculative と通常の差** — 探索候補が全滅しているならしきい値を疑う
5. ここまで見てから配点・mapping の校正に入る

## 7. コマンド早見表

```
探索側
  /test  <id>                    小さく試す（1回1本・公開3本まで）
  /adopt <id>                    通常運用で採用（確信度からレベル自動判定）
  /scale <id>                    生成枠を増やす
  /drop  <id>                    捨てる

制作側
  /approve <id> | /approve all   承認（フラグ付きは一括対象外）
  /reject  <id> 理由             却下
  /status                        キュー状況

実績
  /m <niche> <views> <revenue>   実績を記録（1数字なら revenue のみ）
  /revenue <金額> <ASP名> [メモ]  収益を記録
```

ローカル確認:

```bash
python -m src.pipeline scout --sample     # 探索（APIキー不要）
python -m src.pipeline run --sample       # 制作
python -m src.pipeline report --days 7    # 週次レポート + 台帳
python -m src.pipeline calibrate          # 予測 vs 実績（20件以降）
python -m src.pipeline remind --days 7    # 未更新ニッチのリマインド
pytest -q                                 # テスト
```

## 9. 診断レポートの書式（3条件が発火したとき）

再開条件が発火したら、Claude Code は**変更案を書く前に**この5節で診断を出す。
ChatGPT 側のレビューがこの5点を分離して見る前提なので、書式を合わせておく。

**変更案は5節の判定が出てからにする。** 先に案を書くと、事実と解釈が混ざる。

```markdown
## 1. 事実（数字だけ。解釈を混ぜない）
   採用 N件 / 公開 N件 / Stage分布 / 収益 / 判断時間 / views欠損率
   出典: data/scout/ledger.jsonl の該当行

## 2. 診断（何が起きているか）
   どのファネル段で止まっているか。1つに絞る。

## 3. Ledger 上の根拠
   予測 vs 実績の該当行。predicted_* と actual_* を並べる。
   `monetization_source` が observed か inferred かを必ず示す。

## 4. 整合性チェック
   Stage / likely_cause / diagnosing / commitment が矛盾していないか。
   例: likely_cause=niche なのに commitment が SCALE のまま → 状態遷移の不具合

## 5. 判定（どちらか一方に断定する）
   [ ] 運用障害      → §2 の範囲で今すぐ直す
   [ ] アルゴリズム案件 → 20件未満なら記録のみ。変更しない
   判断できない場合は「データ不足」と書く。推測で埋めない。
```

このルールは §3 の「触らないもの」と同じ性質のもので、**書式そのものを守ることが
思想の維持になる**。事実と解釈を混ぜた診断は、アルゴリズムを触る口実になりやすい。
