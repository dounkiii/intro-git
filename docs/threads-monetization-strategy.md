# Threads 収益化戦略（AI運用・自動化版）

> このリポジトリの自動化パイプライン（収集 → 要約 → 安全チェック → 人間レビュー → 投稿）を
> **Threads 向けに拡張**し、「Claude Code を AI 社員として使い、SNS 運用を自動化して稼ぐ」
> という考え方を、Threads で現実的に実行するための戦略ドキュメントです。

---

## 0. 結論（先に読むところ）

- **Threads は「集客の入口」と割り切る。** Threads 単体の直接収益化（旧ボーナス等）は
  2026 年時点で日本の一般ユーザーには実質閉じています。Threads で稼ごうとしない。
- **収益は note とアフィリエイトで作る。** この戦略の稼ぎ方は次の 2 本柱に集中します。
  - **① note** … 無料記事で信頼を積み、**有料note / 有料マガジン / メンバーシップ**で課金
  - **② アフィリエイト** … 記事・プロフィールリンクから ASP 案件を紹介して成果報酬
- **導線はシンプルに1本。** `Threads(集客) → プロフィールの1リンク → note(収益化ハブ)`。
  note の記事内でアフィリエイトも回すので、**リンク先を note に一本化**できる。
- **勝ち筋は「量 × 一貫性 × 検証」。** ここを人力でやると続かないので、
  **収集・下書き生成・スケジューリングを自動化し、人間は最終レビューだけ**を行う。
  → まさにこのリポジトリのパイプラインが担う役割です。
- **やってはいけないこと**を先に決める（誹謗中傷・未確認情報の断定・なりすまし・
  規約違反の自動化・ステマ）。既定で `DRY_RUN=true` / `REVIEW_REQUIRED=true`。

## 1. Threads で「稼ぐ」とはどういうことか（2026 年の現実）

### 1.1 直接収益化は当てにしない
- 旧 **Threads ボーナスプログラム**（招待制・最大月 $5,000）は 2025 年に新規募集が終了。
  日本での招待実績はもともと極めて少数でした。
- サブスク／投げ銭／"Creator Fast Track"（他 SNS で 10 万フォロワー級向け固定給）などは
  一部でテスト・限定提供されるものの、**始めたばかりのアカウントの収益源にはなりません。**

### 1.2 本命は「間接収益化」
Threads は「発見性が高く、テキスト主体で会話が伸びやすい」プラットフォーム。
フォロワーとの距離が近く、**信頼を積んで外部の収益ポイントに送客する**のが最も現実的です。

| 収益モデル | 概要 | 立ち上げ難易度 | 収益化までの目安 |
|---|---|---|---|
| アフィリエイト | 投稿・プロフィールリンクから商品/サービスを紹介 | 低 | 1〜3 か月 |
| 自社商品・サービス | 電子書籍・テンプレ・講座・受託などへ送客 | 中 | 2〜4 か月 |
| リード獲得 | メルマガ/LINE 登録 → 後日オファー | 中 | 2〜4 か月 |
| 他 SNS へ送客 | YouTube/ブログ/X の収益に合流させる | 低 | 併用で加速 |

## 2. 「AI 社員で回す」という考え方（元記事のアプローチ）

元記事のポイントは **「Claude Code を AI 社員として雇い、運用の 7 割を自動化する」** ことです。
Threads 運用に落とすと、役割分担はこうなります。

| 工程 | 担当 | このリポジトリの対応モジュール |
|---|---|---|
| ネタ収集（トレンド/一次情報） | AI | `collectors/`（X から収集。将来: RSS/ニュース API を追加） |
| 話題度スコアリング・分類 | AI | `processing/classifier.py` |
| 安全性チェック（誹謗中傷/未確認情報） | AI | `processing/safety.py` |
| 投稿文（フック/本文/CTA）生成 | AI | `processing/summarizer.py`（Threads 用ビルダーを追加） |
| **最終レビュー・承認** | **人間** | `publishers/review_queue.py` |
| Threads へ投稿 | AI | `publishers/threads.py`（本ブランチで追加） |
| スケジュール実行 | AI | `scheduler.py` |

**人間がやるのは「最終レビューと戦略判断」だけ**にするのが継続の鍵。
1 日 15 分のレビューで回せる状態を目指します。

## 3. アカウント設計（最初の 1 週間でやること）

1. **ニッチを 1 つに絞る。** 「AI 活用 × 個人の生産性」「副業の始め方」「節税・お金」など、
   **自分が一次情報を出せる／継続して語れる**テーマを選ぶ。雑多にしない。
2. **プロフィール最適化。**
   - 1 行目：誰の何を解決するか（例:「AIで“ひとり作業”を10倍速にする方法を毎日」）
   - 実績・権威づけを 1 つ
   - **リンクは 1 つに集約**（アフィリLP or LINE/メルマガ or リンクまとめ）
3. **投稿フォーマットの型を 3〜5 個用意**（後述）。
4. **最初の 30 投稿ぶんのネタリスト**を作る（AI に壁打ちさせる）。

## 4. コンテンツ戦略（Threads で伸びる型）

Threads は **「テキストの読みやすさ」「共感」「会話（リプが伸びる）」** が評価されやすい。
動画前提の TikTok とは別に、**テキスト最適化**した投稿ビルダーを使います。

### 4.1 伸びる投稿の型
- **フック（1 行目）が全て。** スクロールを止める一文を最初に置く。
  - 数字・逆説・断定・具体的な悩み（例:「フォロワー0でも“これ”だけはやめとけ」）
- **本文は短く・改行多め。** 1 投稿 500 字以内、要点は 3 つまで。
- **CTA を必ず入れる。** 「保存」「フォロー」「コメントで質問」「プロフィールのリンク」。
- **1 日 2〜5 投稿**を目安に、**時間を分散**（朝/昼/夜）。

### 4.2 コンテンツの配分（黄金比の目安）
- 60%：**価値提供**（ノウハウ・気づき・まとめ）→ 信頼とフォロー獲得
- 30%：**共感・ストーリー**（失敗談・過程・意見）→ 会話とファン化
- 10%：**オファー**（アフィリ/自社商品/登録）→ 収益化

> 収益投稿を出しすぎると伸びが落ちる。**価値提供で信頼残高を貯めてから**オファーする。

### 4.3 このパイプラインでの生成
`Summarizer.build_thread()`（本ブランチで追加）が Topic から
**フック → 本文（要点 3 点）→ CTA → ハッシュタグ**の Threads 投稿文（`ThreadsPost`）を生成します。
`config.yaml` の `threads` セクションで CTA やハッシュタグ、文字数上限を調整できます。

## 5. 収益化の導線（note × アフィリエイト）

集客は Threads、収益化は note とアフィリエイト。お金の流れはこの1本に統一します。

```
[Threads 投稿]  →  [プロフィールの1リンク]  →  [note（収益化ハブ）]
  価値提供で信頼          計測（UTM/短縮URL）        ├─ 無料記事：信頼づくり・回遊
  60:30:10 で運用                                    ├─ 有料note：単発課金（¥300〜¥1,000）
                                                      ├─ 有料マガジン：まとめ売り
                                                      ├─ メンバーシップ：月額の安定収益
                                                      └─ 記事内アフィリエイト：ASP 成果報酬
```

### 5.1 note で稼ぐ
- **無料 → 有料の階段を作る。** 無料記事で「役に立つ人」と認識させ、
  一歩踏み込んだノウハウ・テンプレ・事例を**有料note**にする。
- **価格の目安。** 入口は ¥300〜¥500 で買われやすく。実績が出たら ¥1,000 前後や
  **有料マガジン**（複数記事の束）へ。継続収益は**メンバーシップ（月額）**で作る。
- **回遊設計。** 各記事の末尾に関連記事・有料note・マガジンへのリンクを必ず置く。
- **Threads との連動。** Threads で「気づき」を投稿 →「詳しくは note に全部書いた」で送客。
  投稿はティザー（さわり）、結論と手順は note、という役割分担にする。

### 5.2 アフィリエイトで稼ぐ
- **note 記事の中で回す。** レビュー・比較・使い方記事の文脈で自然に紹介するのが最も成約する。
  Threads に直リンクを貼るより、**note 経由**のほうが規約的にも安全で説明も尽くせる。
- **ASP を用意。** A8.net / もしもアフィリエイト / 楽天・Amazon アソシエイト /
  各種サービスの公式パートナープログラムなど、テーマに合うものを 1〜2 個に絞る。
- **紹介するのは「自分が使って良かったもの」だけ。** 信頼が資産。安売りしない。
- **PR 表示は必須。** アフィリエイト/広告を含む投稿・記事には「#PR」「広告」を明記
  （ステマ規制・景表法）。→ §8 参照。

### 5.3 計測と改善
- **リンクに計測を付ける。** プロフィールの note リンクに UTM や短縮 URL を使い、
  「どの Threads 投稿が note 流入・売上に効いたか」を週次で見る。
- **勝ちパターンに寄せる。** 売れた記事・伸びた投稿の型を特定し、そこに投稿量を集中させる。

## 6. 90 日ロードマップ

### Phase 1（0〜30 日）: 型づくりと習慣化
- ニッチ確定・プロフィール最適化・リンク 1 本化
- パイプラインを **`DRY_RUN=true` で回し、下書きの質を人間レビューで調整**
- 1 日 2〜3 投稿。**バズより「毎日出す」を優先。**
- KPI: 投稿数、プロフィールアクセス、フォロー転換率

### Phase 2（31〜60 日）: note と収益導線の設置
- 反応の良い型・テーマを 2〜3 個に集中（データで判断）
- **note を開設**し、無料記事を数本 → **最初の有料note（¥300〜¥500）**を用意
- プロフィールのリンクを **note に一本化**、Threads はティザー→note へ送客
- ASP に登録し、note 記事の中でアフィリエイトを 1〜2 案件だけ検証
- KPI: 保存/コメント率、note 流入クリック、有料note の販売数

### Phase 3（61〜90 日）: 収益の最適化とスケール
- 売れた記事・伸びた投稿の型に投稿量を寄せる
- **有料マガジン / メンバーシップ（月額）**で継続収益を作る／単価を上げる
- スケジューラで投稿を自動分散、レビューは 1 日 15 分に圧縮
- 横展開（2 本目のアカウント or 他 SNS 合流）を検討
- KPI: 収益額、note の CV 率、メンバーシップ継続率、LTV

## 7. KPI とレビュー運用

| 指標 | 何を見るか | 頻度 |
|---|---|---|
| 投稿数 | 継続できているか | 毎日 |
| インプレッション/プロフィールアクセス | 発見性 | 週次 |
| フォロー転換率 | プロフィールの魅力 | 週次 |
| 保存・コメント率 | コンテンツの刺さり | 週次 |
| リンククリック | 導線の強さ | 週次 |
| 登録数・収益 | 収益化の成否 | 週次/月次 |

**週次レビュー会（AI に集計させ、人間が意思決定）**を 30 分。
「伸びた投稿の共通点は？」「収益に効いた導線は？」を毎週更新する。

## 8. リスク・コンプライアンス（必読）

このリポジトリの安全思想を Threads でもそのまま適用します。

- **既定で `DRY_RUN=true` / `REVIEW_REQUIRED=true`。** 全自動の無審査投稿はしない。
- **誹謗中傷・個人攻撃・なりすまし・未確認情報の断定を投稿しない**
  （`processing/safety.py` のガードレールを適用）。
- **アフィリエイト/PR は明示する**（ステマ規制・景表法。「#PR」「広告」を明記）。
- **プラットフォーム規約と API 規約を守る**（自動化の上限、スパム的挙動の禁止、
  Threads/Meta の利用規約）。過度な自動リプ/フォロー/大量投稿はアカウント凍結リスク。
- **一次情報を優先**し、引用元を示す。
- **著作権・肖像権**に配慮（他人の画像/文章の無断転載をしない）。

> 「稼ぐ」より先に「凍結されない・訴えられない」を守るのが、結局いちばんの近道です。

## 9. このリポジトリでの実行手順

```bash
# 依存インストール
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # THREADS_ACCESS_TOKEN / THREADS_USER_ID などを設定

# 1) ネタ収集〜Threads下書き生成〜レビューキュー投入（DRY_RUN 既定）
python -m src.pipeline run --sample          # まずはサンプルで型を確認

# 2) 下書きを人間がレビュー・承認
python -m src.pipeline review --list
python -m src.pipeline review --approve <ITEM_ID>

# 3) 承認済みを Threads へ投稿（DRY_RUN=false のとき実投稿）
python -m src.pipeline publish --approved --target threads

# 4) 定期実行
python -m src.scheduler --interval 3600
```

### 必要な環境変数（`.env`）
| 変数 | 説明 |
|---|---|
| `THREADS_ACCESS_TOKEN` | Threads API（Meta Graph API）のアクセストークン |
| `THREADS_USER_ID` | 投稿先の Threads ユーザー ID |
| `DRY_RUN` | `true`（既定）で実投稿せず内容をログ出力 |
| `REVIEW_REQUIRED` | `true`（既定）で承認前は投稿しない |

> Threads API はアプリ登録・権限取得が必要です。取得できるまでは `DRY_RUN=true` のまま
> 下書きの質を磨き、型とネタのストックを作る期間に充てるのが効率的です。

## 10. まとめ

1. **Threads は集客の入口。収益は note（有料記事/マガジン/メンバーシップ）とアフィリエイトで作る。**
2. **価値提供 6：共感 3：オファー 1** で信頼を積み、プロフィールの **note リンク1本**に送客する。
3. **収集・下書き・投稿を自動化し、人間はレビューと戦略だけ**——このパイプラインがそれを担う。
4. **安全第一**（DRY_RUN / レビュー必須 / 誹謗中傷・ステマ回避・PR明記）で、続けられる運用にする。
