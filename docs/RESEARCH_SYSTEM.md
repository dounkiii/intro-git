# 探索レイヤ設計 — ちゃっぴー案のレビューと合体版

ChatGPT 案（Grok → Gemini → GPT の3段リサーチ）をレビューし、既存の制作パイプラインと
統合した設計。**採用した部分・変えた部分・その理由**を明示する。

---

## 1. レビュー

### 採用した部分（そのまま or ほぼそのまま）

| 項目 | 評価 |
|---|---|
| **「まだ競合が少ないのに伸び始めている兆候」を狙う** という中核思想 | ここが一番良い。既存パイプラインはニッチ固定だったので、この探索レイヤが欠けていた |
| 100点満点の評価軸（需要20/競合15/収益性20/成長15/コンテンツ化10/アフィリ10/継続5/信頼5） | 配点まで妥当。**そのまま採用**（`src/scout/models.py` の `RUBRIC`） |
| now / watch / drop の3段判定 | 判断が一発で決まるので採用 |
| 「今日の1位」の出力フォーマット | スマホで読む形として良い。**そのまま採用**（`src/scout/report.py`） |
| 上位だけ提示（大量に見せない） | 採用。見なくなったら終わりなので正しい |
| MVP から始めて段階的に足す | 採用 |

### 変えた部分（3点）

#### ① 3社の API を使う理由がない → **2社に減らした**

役割分担は綺麗に見えるが、実際にやっているのは (a) SNS検索 (b) Web検索 (c) 統合評価の3つで、
**(b) と (c) は 1 モデルで両方できる**。3社に分けると、キー・課金・レート制限・SDK差分・
障害点が3倍になる。MVP でこれは自殺行為。

| ちゃっぴー案 | 合体版 | 理由 |
|---|---|---|
| Grok: SNS発掘 | **Grok（維持）+ X API（追加）** | X 上の空気を読む部分は他モデルで代替しにくい。ただし Grok の「伸びている」判断は LLM の主観なので、X API から**いいね/時間を実測**して併用する |
| Gemini: Web調査 | **Claude の `web_search` サーバーツール** | 検索・読解・構造化が1リクエストで完結する。3社目を保守する価値がない |
| GPT: 統合・評価 | **Claude（structured outputs）** | JSON スキーマで出力を固定できるので、パース崩れで承認キューが汚れない |

Grok を残したのは温存ではなく、**X の本文アクセスが本当に代替しにくい**から。
無効化しておけば X API だけで動くし、両方無くてもサンプルで全体が回る。

#### ② スコアが出ることと儲かることは別 → **主観と実測を分離した**

ちゃっぴー案の致命的な弱点。**LLM は「競合の少なさ」を検索せずに推測で答えられてしまう。**
自信満々に「競合が少ないです、15点」と書く。これはただの占いで、意思決定に使えない。

合体版は 2 段構えにした（`src/scout/scoring.py`）。

1. **LLM 採点（主観）** — 評価軸どおりに 100 点満点で採点させる
2. **実測シグナルで補正（客観）**

| 実測 | 補正 |
|---|---|
| 検索で見えた独立ドメインが閾値以上なのに「競合が少ない」と採点 | **-10** ＋ 矛盾フラグ |
| 根拠 URL が 0 件 | **-8** ＋ 矛盾フラグ |
| いいね/時間が閾値未満（X 発掘） | **-5**（「伸び始めている」の否定） |
| いいね/時間が閾値の4倍以上 | **+5** |
| 何度も観測されているのに伸びていない | **-5**（継続性ではなく陳腐化） |
| 過去に実際に収益が出たキーワード | **+5**（成果フィードバック） |

矛盾（`conflicts`）はレポートに `⚠️ LLMと実測の食い違い` として出る。
**LLM を疑える形で人間に渡すこと**が、この設計の主目的。

さらに、順位付けは合計点ではなく **`early_signal = 成長性 × 競合の少なさ`** を主軸にした。
合計点で並べると「すでに大流行しているテーマ」（需要20・成長15・競合1）が上位に来て、
システムの目的と真逆になる。テストで固定してある
（`tests/test_scout_scoring.py::test_順位付けは合計点より早期シグナルを優先する`）。

#### ③ 最大の欠陥: 発掘しても何も作られない → **制作パイプラインに直結した**

ちゃっぴー案は「毎日 TOP3 が出てくる」で終わっている。
**情報収集システムはこれで必ず死ぬ。** 3日で見なくなって終わる。

合体版は `/adopt <id>` を出口に置いた。

```
探索レイヤ  発掘 → 裏取り → 採点 → 日次レポート Issue
                                          │
                        通勤中に  /adopt <id>
                                          ▼
                          data/adopted_niches.yaml
                                          │
制作レイヤ  収集(このクエリで) → 台本/記事 → 承認Issue → /approve → 投稿
                                          ▼
                              収益ログ (data/revenue.csv)
                                          │
                        `/revenue 3200 A8 インボイス`
                                          ▼
                          探索レイヤのスコアに +5 で還る
```

これで **リサーチ → 制作 → 投稿 → 成果 → スコア** が閉じる。
人間の判断は 2 種類だけになる。

- **週1〜数日に1回**: `/adopt` — どのニッチを攻めるか
- **毎日3〜5分**: `/approve` — 出てきた原稿を出すか

### その他の指摘

| 指摘 | 対応 |
|---|---|
| DB / Notion / Sheets は MVP には過剰 | **JSONL + git** にした。履歴と監査ログが無料で付き、Actions のランナーが破棄されても状態が残る |
| Discord / Slack / Telegram 通知 | 不要。GitHub Issue が既に通知面として機能している（アプリのプッシュ通知が来る） |
| 「過去ネタとの比較」を後回しにしている | **MVP に入れた。** 後回しにすると絶対入らないし、同じネタを毎日出すシステムは即座に見捨てられる |
| 重複は「捨てる」ではなく統合すべき | 3日連続で出て**伸びている**ネタは初出より有望。観測回数と伸びを追跡し、伸びなければ減点する形にした |
| 収益化候補に「情報商材」が入っている | 外した。既存 PLAYBOOK で地雷に分類している（ステマ規制・特商法・返金トラブル） |
| YMYL への言及がない | リスク項目に含めるようプロンプトに明記。お金ジャンルは検索評価が厳しい |
| Grok のモデル名 | 変わるので `config.yaml` で指定する形にした。既定値は動かない可能性がある（[docs.x.ai](https://docs.x.ai/) で確認） |

## 5. MVP 実装手順（実施済み）

ちゃっぴー案の MVP 定義（発掘 → 評価 → TOP3 → 保存）に沿ったが、
③の理由で **`/adopt` までを MVP に含めた**（出口が無いと価値が出ないため）。

1. ✅ データモデル（`models.py`）— 評価軸・early_signal・トークン正規化
2. ✅ 発掘元アダプタ（`sources/`）— X API（実測付き）+ Grok（任意）
3. ✅ 裏取り（`research.py`）— Claude web_search + 実測ドメイン数
4. ✅ 採点（`scoring.py`）— 100点採点 + 実測補正 + 保守側判定
5. ✅ 永続化と重複統合（`store.py`）— JSONL、観測回数の追跡
6. ✅ レポート（`report.py`）—「今日の1位」+ 矛盾の明示
7. ✅ ニッチ採用（`niches.py`）— 制作レイヤへの接続
8. ✅ CLI（`python -m src.pipeline scout`）と Actions（`daily-scout.yml`）
9. ✅ テスト 27 件

### 次に足すもの（優先順）

| 優先 | 項目 | 理由 |
|---|---|---|
| 高 | **検索ボリュームの実測** | 現状「競合の少なさ」は検索結果のドメイン数が代理指標。実際の検索需要は測れていない |
| 高 | **採用ニッチ専用のアフィリ案件** | いまは `offers.default` に落ちる。ニッチごとに単価の高い案件を割り当てたい |
| 中 | 既存記事の質の評価 | ドメイン数だけでは「競合が多いが全部薄い」を見分けられない |
| 中 | 採用ニッチの自動休止 | 30日で収益0のニッチは自動で `active: false` にする |
| 低 | Gemini / GPT の追加 | 現状の構成で困ってから。困っていないうちに増やすと保守が破綻する |

## 7. コスト感

`research_limit: 6`（既定）で 1 日あたり Claude API 呼び出しは
**裏取り6回（web_search 付き）+ 採点6回 = 12回**。
制作レイヤの台本・記事生成が別途 1 本あたり 2 回。

`config.yaml` の `scout.research_limit` と `llm.effort` が主なコスト調整点。
API 代を下げたいときは `research_limit` を先に絞る（採点より検索の方が高い）。

# 第2ラウンド — GPT の改訂案へのレビューと実装

GPT が改訂案（Evidence 層 / Discovery・Business 分離 / SERP Weakness / 検索需要実測 /
ファネル別撤退 / Experiment Ledger / explore-exploit / 条件付き Gemini）を出してきた。
実装者として、**費用対効果が悪い部分**と**今MVPに絶対入れる部分**を分けて判定した。

判定基準は1つだけ。**最短で最初の売上に効くか。**

## 判定表

| # | GPT提案 | 判定 | 理由 |
|---|---|---|---|
| ② | observed が inferred を**置き換える**（足し引きしない） | ✅ **MVP実装済** | 正しい。旧実装の -10 は汚いハックだった。新規APIゼロ |
| ③ | Discovery / Business / Opportunity = √(D×B) | ✅ **MVP実装済** | 正しい。「入る余地はあるが金にならない」を排除できる。新規APIゼロ |
| ⑧ | 収益+5 を廃止し explore/exploit 予算に | ✅ **MVP実装済** | 指摘どおりループになる。新規APIゼロ |
| ⑨ | Experiment Ledger（予測の凍結） | ✅ **MVP実装済** | 記録だけ。分析機構は作らない |
| ⑦ | ファネル別撤退（時間ではなく試行回数） | ✅ **MVP実装済**（手入力） | 30日基準より正しい。ただし指標取得は API 審査が重いので `/metrics` 手入力から |
| ⑩ | 目的関数 = 人間の注意1単位あたり期待収益 | 🟡 **フレームのみ採用** | EV式は却下（下記）。分母（判断時間）だけ実測して可視化 |
| ④ | SERP Weakness Score | 🟡 **概念採用・データ源は代理** | 考え方は正しい。実SERPは有料APIなので無料の代理指標＋低confidenceで入れた |
| ⑤ | 検索需要の実測（Google Ads API） | ❌ **初売上まで延期** | 下記。**優先度1位に置くのは反対** |
| ① | 条件付き Gemini クロスチェック | ❌ **延期（おそらく不要）** | 下記 |
| ⑥ | 配点は変えず実績に決めさせる | ✅ **完全同意** | 素点100 / Discovery / Business を並列保存済み |

## 反対した3点の理由

### ⑤ Google Ads API を優先度1位にするのは反対

**Google Ads API のキーワード検索数取得には、承認済みデベロッパートークンが必要。**
Basic access は通常、稼働中の広告アカウント（＝出稿実績）が前提になる。
つまり **1円も稼いでいない段階で、審査待ちと広告費が先に発生する。**
Google Trends 公式 API も 2026年8月時点で Alpha・限定アクセス（GPT自身が認めている）。

もっと本質的な反論: **0円の段階で検索ボリュームは制約になっていない。**

売上が出ない原因は「やや検索数の少ないニッチを選んだ」ことではなく、
(a) 換金経路が無い (b) 公開していない、のどちらかである。
ボリュームが効くのは「有望ニッチが20個あってどれを選ぶか」という状況で、
それは3ヶ月目の問題であって1週目の問題ではない。

**対案**: `production_fit` に「自前の `AFF_*` で換金経路が組めるか」の実測を入れた
（`Scorer._has_route`）。これは**今すぐ・無料・確実**に測れて、しかも (a) を直接潰す。
有料の検索需要APIは、広告出稿実績を要求しない従量課金型（DataForSEO 等）を
**初売上の資金で**入れる。順序を逆にしない。

### ① 条件付き Gemini は、おそらく永久に不要

GPT の条件設定（根拠が少ない / 矛盾している / now-watch境界）は妥当。
ただし **その条件が発火する場面こそ、④⑤で実データを入れるべき場面**である。

「競合が多いか少ないか」で意見が割れているとき、必要なのは**2つ目のLLMの意見**ではなく
**1つ目の実測データ**。SERP を実測すれば意見の相違そのものが消える。
LLM を2つ並べて多数決を取るのは、どちらも推測である限り精度が上がらない。

**同じ複雑さ予算を使うなら、Gemini より SERP API に使う。** これが実装者の判断。
（インターフェースは `SerpAnalyzer(provider=...)` で開けてあるので、
本当に必要になったら差し込める）

### ⑩ EV式を今スコアに使うのは反対（フレームは採用）

```
EV = P(traffic) × P(click) × P(CV) × commission − cost
```

**この4つの確率は N=0 では推定できない。** 推定できない数値を4つ掛けると、
「精密そうに見える捏造」が出てくる。これは②で今まさに直した「占い」問題の再発で、
しかも小数点付きなので粗いスコアより悪い（人間が信じてしまう）。

**対案 — EV を「予測」ではなく「実測KPI」として先に立てる:**

| 項 | 今できること |
|---|---|
| 分母（人間の注意） | **実測できる。** 承認・採用のたびに秒数を積算（`ExperimentLedger.record_attention`） |
| 分子（収益） | **実測できる。** `/metrics` の revenue |
| P(traffic/click/CV) | **推定しない。** `/metrics` の実績から後で回帰する |

つまり `判断1分あたり収益` を**今日から実測して表示する**。予測式は Ledger に
20件溜まってから当てはめる。

さらに実装者として言い添えたいこと: **N=0 における EV の最大のレバーは順位精度ではない。**
週1採用・1日5分の運用では、ランキングを 10% 改善しても絶対値はほぼ動かない。
効くのは「判断1回あたりの秒数を削る」か「公開率を上げる」方。
だから Ledger は収益より先に**注意時間**を可視化している。

```
                        heuristic(無料/代理/confidence 0.45固定) | dataforseo | serpapi
src/scout/explore.py    explore/exploit 予算。採用済みと語が重なるかで振り分け
src/scout/funnel.py     Stage1〜5 の切り分けと、試行回数ベースの撤退判定
src/scout/ledger.py     予測の凍結・実績追記・注意時間の積算・校正ゲート
```

`Score` は素点100点を保ったまま、`discovery` / `business` / `opportunity` を並列で持つ
（GPT提案⑥）。`llm_total`（推測のみ）と `total`（実測込み）も両方保持するので、
「実測導入で何点動いたか」が後から検証できる。

## スコアの構造

```
opportunity = √(discovery × business)          ← 最終順位

discovery = momentum × whitespace × confidence
            成長性     競合の空き   根拠の信頼度
            ↑x_velocity ↑SERP分類   ↑実測で埋まった軸の割合で上がる

business  = demand × monetization × production_fit
            需要      収益化       制作相性
                     ↑収益性+アフィリ相性  ↑AFF_*で換金経路が組めるか(実測)
```

`confidence` を discovery に掛けているので、**根拠が薄い候補は自動的に順位が下がる**。
実測が1つも無い初期は全候補が等しく割り引かれるため、順位自体は歪まない。

## 残っている弱点（正直に）

1. **SERP は代理指標**。Google の実際の順位ではなく `web_search` の結果を分類している。
   `confidence` を 0.45 に固定して「実測を騙らない」ようにしてあるが、本物ではない
2. **検索ボリュームは未実測**。上記の理由で初売上後に回した
3. **`/metrics` は手入力**。週1回30秒だが、忘れると Ledger が育たない
4. **換算ルール（observed→点数）は人間の仮説**。`mapping_version` を打ってあるだけで、
   まだ校正されていない。ここは Ledger が20件溜まるまで動かせない

GPT の順位と違う部分がある。理由は「初売上までの距離」で並べ替えたため。

# 第3ラウンド — 収束。confidence の扱いと /metrics 運用を修正

GPT が反論3点（検索需要APIの優先度 / Gemini不要 / EV式を予測に使わない）をすべて受け入れ、
代わりに**設計上の重要なバグを1つ指摘してきた**。それが正しかったので直した。

## GPT の指摘（採用）: confidence を Discovery に掛けてはいけない

第2ラウンドの実装はこうだった。

```
discovery = 成長性 × 競合の空き × confidence
```

一見もっともらしいが、**早期発見システムとして逆に働く**。

本当に早いトレンドほど、ソースが少なく、観測回数も少なく、SERP がまだ形成されていない。
つまり **早い → 根拠が薄い → confidence が低い → 順位が落ちる**。
これでは成熟したネタを好むシステムになる。目的と真逆。

修正:

```
discovery = 成長性 × 競合の空き        ← confidence は掛けない
confidence = 0〜1                      ← 不確実性として別に持つ
```

そのうえで confidence の使いどころを3つに分けた。

| 用途 | 扱い |
|---|---|
| **順位** | 使わない（上記の理由） |
| **表示** | 「機会スコア 82 / 確信度 0.31」と並べる。「82点だが不確実」と人間が読める |
| **`now` 判定のゲート** | 使う。低確信で自動的に本気の投資はさせず watch に留める |
| **explore 枠** | 「高スコア × 低確信」を🎲マークで明示し、上位に1件繰り上げる |

4つ目は実装者側の追加。GPT は「explore 枠では高Opportunity+低Confidenceを意図的に試す
価値がある」と書いていたが、ランキングに任せると埋もれる。明示的に繰り上げないと
「確信が高いものだけ試す」に収束して学習が進まない。

## その他の採用点

### いいね/時間を log 変換にした（線形をやめた）

SNS 指標の分布は 10 / 20 / 40 / 80 / 160 / 1000 / 10000 のように極端に歪む。
「閾値の4倍で満点」の線形換算だと上位が飽和し下位が過大評価される。

```
旧: ratio = velocity / (閾値 × 4)              線形
新: ratio = log1p(velocity) / log1p(閾値 × 20)  対数
```

最終的には同一プラットフォーム・カテゴリ内の percentile にしたい
（上位10% → 15点、中央値 → 7点）。分布が取れるまでは log で近似する。
SERP weakness は既に 0-100 に正規化された複合指標なので線形のままでよい。

### SERP に特徴量を3つ追加

| 特徴量 | 意味 | 補正 |
|---|---|---|
| **Intent Fragmentation** | 上位が解説/商品/掲示板/ニュースで混在 = Google も決定版を持っていない | +12 |
| **Answer Coverage** | 「〜方法」「比較」等が無く「〜とは」「公式」ばかり = 答えが供給されていない | +12（低いとき） |
| **Domain Concentration** | 同一ドメインが枠を占有。強者独占とも「他に無い」とも読めるので補助扱い | -5（小さく） |

ホスト名で「弱い」と固定しない方針も採用した（note にも強い記事はある）。
ページ種別は特徴量の1つに留めている。

### Stage 判定をプラットフォーム別 + 自アカウント baseline に

絶対値のベンチマークを信用しすぎない。判定の基準はこの順でフォールバックする。

1. **自アカウントの実績中央値**（10件以上溜まったら。中央値 × 0.3 を配信失敗ライン）
2. **プラットフォーム既定**（TikTok / YouTube Shorts / X で別。Shorts はサムネ表示と
   実視聴の差が大きいので1投稿あたり下限を高く、反応率下限を低く）
3. 絶対値の仮値

### 最重要KPI を2つ立てた

GPT の提案「初売上までに何件 adopt したか」を採用。ただし**一度しか観測できない遅行指標**
なので、毎週見られる先行指標を並べた。

- **初売上までの採用件数**（3件なら探索が効いている / 20件超で0円なら根本的に間違い）
- **公開到達率**（採用したニッチのうち1本以上公開できた割合）
  ← 採用しても公開に至っていなければ、下流のスコア精度をいくら上げても意味がない

### explore 比率を固定せず状態から決める

```
winner 0件 → 100% explore   （exploit 対象がそもそも無い）
      1件 →  30%
      3件 →  20%
      5件 →  15%
```

## 最重要課題だった `/metrics` を4段構えで潰した

「人間に全数字を入力させない」が GPT の回答で、これが正しい。

| 段 | 対策 | 実装 |
|---|---|---|
| 1 | **自前で分かるものは自動入力** | `posts` は `data/posts.csv` から自動集計。人間に数えさせない |
| 2 | **入力は累計値でよい** | 差分はシステムが計算する。人間に引き算をさせない |
| 3 | **必須は金側だけ** | `/m <niche> 3200` の1数字でも受け付ける |
| 4 | **入れなくても止まらない** | Stage 0（判定不能）として記録し UNKNOWN のまま前に進む |

入力形式は個数で意味が決まるので曖昧にならない。

```
/m xxx 3200                  → revenue
/m xxx 6000 3200             → views, revenue
/m xxx 6000 45 1 3200        → views, clicks, conversions, revenue
/m xxx views=6000 revenue=3200  → 名前付き（順不同・混在可）
```

**Core / Diagnostic の分離も入れた。**

- Core（Stage 判定に必要）: `posts` / `views` / `revenue`
- Diagnostic（取れたときだけ）: `engaged` / `clicks` / `conversions`

実装者側の追加として **Stage 0（判定不能）を明示**した。views が未入力のとき
Stage 1（配信されない = ニッチが悪い）と Stage 4（売れない = 案件が悪い）は区別できない。
区別できないものを Stage 1 と診断すると、**良いニッチを誤って捨てる**。
「取れていない」を「悪い」と読み替えないのは、Diagnostic 全体に適用した原則。

さらに `weekly-metrics.yml` を追加した。未更新の採用ニッチだけを、
そのまま数字を書き換えてコメントできる形で週1回 Issue に出す。
