## 前提（初めて読む場合はここだけで足ります）

通勤中にスマホのコメント1行で回す副業パイプライン。2レイヤ構成です。

設計は凍結済みです。変更してよい条件は3つだけ（初売上 / Test+Adopt 20件で売上0 /
5件レビューで同じ運用異常が2回連続）。詳細は `docs/OPERATIONS.md`。

## 今回の論点: 「非対称バグ」が5件出ている

運用開始から実装バグ12件を直しました（一覧は `docs/RESEARCH_SYSTEM.md` の
「運用フェーズで直した実装バグ（台帳）」）。そのうち **5件が同じ形**でした。

| # | 片側は知っていた | 反対側は知らなかった |
|---|---|---|
| 1 | 探索側: トークン無しならスキップするガード | 制作側: 無かった → 401 で全滅 |
| 6 | 制作側: `AFF_*` を渡してあった | 探索側: 無かった → 換金経路が常に未検出 |
| 9 | 探索側: `llm_provider` を台帳に記録 | 制作側: 捨てていた → 承認画面が誤表示 |
| 11 | builder: 尺の上限を知っている | 台本生成側: 知らない → 上限90秒に対し実測115秒 |
| 12 | スコアリング層: 換金経路の実在を知っている | 診断層: 知らない → 提携前の0円を「案件が悪い」 |

**#12 が一番影響が大きかった**ので詳細を書きます。Stage 4（クリックはあるが
成約しない）が無条件で `CAUSE_OFFER` を返し、処方が「案件を変える」でした。
提携審査が通る前は直接の換金経路が存在しないので、変える案件が無いのに
「案件を変えろ」と言う実行不能な指示になっていました。さらに `CAUSE_OFFER` は
`DIAGNOSING_CAUSES` に含まれるため生成枠が1本に絞られ、配信もクリックも
成立している唯一のニッチをオーナーの提携申請待ちで減速させていました。

直し方は既存の Stage 0（判定不能）と同じ思想に寄せました。

- `AffiliateEngine.has_direct_offer()` を追加（`hub_url` は数えない。ハブは
  案件が通るまで収益への道を閉じないための fallback で、案件そのものではない）
- `FunnelMetrics.direct_route` に実測を渡す（`None` = 未記録）
- `direct_route is False` の Stage 4 は `CAUSE_NOT_MONETIZED`（判定不能）に分岐し、
  処方を「提携申請を通す（オーナー側の作業）」にする
- `next_level` は診断中フラグを立てずレベルを維持する（生成枠を絞らない）

これで「収益0を『このニッチは売れない』という教師データにしない」が、
撤退判定だけでなく診断ラベルと生成枠の両方で成立します。

## 聞きたいこと

### (1) レイヤ境界の契約をコード化する方法

前回「統合は不要。ただし『レイヤ境界の契約』をコード化した方がいい」という
回答をもらいました（この方向に同意です。探索と制作を別サイクルで回す利点は
残したい）。**具体形について意見が欲しいです。**

いま考えている案は3つです。

**案A: 実測値の受け渡し表を1ファイルに集約する**
`src/scout/contract.py` のような場所に「レイヤ間で渡す実測値」の一覧を
定数として置き、両側がそこを参照する。渡し忘れは import されない定数として
残るので目視で気づける。ただし強制力は無い。

**案B: 対称性テストを書き続ける（現状の方針）**
`config.yaml` から必要スロットを導出して3ワークフロー全部を検証する、
全プロバイダが `api_key_env` を持つことを検証する、状態をコミットする
ワークフローが push 前に pull することを検証する、など。
すでに #6 以降はこれで書いています。強制力はあるが、**バグの形を知ってから
しか書けない**（5件とも事後に書いた）。

**案C: 観測値を1つのデータクラスに閉じ、両レイヤがそれを受け取る**
`Evidence` / `Score` / `FunnelMetrics` に散っている観測値を1つの
`ObservedState` に集約し、探索・制作・診断がすべてそれを引数に取る形にする。
一番強制力があるが、凍結中のクラスに手が入るので影響範囲が大きい。

**質問**: 案A/B/C のどれか、あるいは別の形か。特に知りたいのは
**「バグの形を知る前に落とせる仕組み」があるか**です。案Bは事後的にしか
書けないのが弱点だと思っています。

### (2) 提携前の期間に取るべき指標

`direct_route is False` の期間は「収益は判定不能」にしました。この期間に
**代わりに何を見ておくべきか**を決めたいです。いま取れるのは posts / views /
revenue（Core）と engaged / cta_clicks / conversions（Diagnostic、任意）です。

私の考えは「`cta_clicks` を優先して取る」です。ハブリンクへのクリックが
出ているかどうかは提携の有無に関係なく測れて、提携が通った瞬間に
Stage 3 と Stage 4 を切り分ける材料になるからです。ただし `/metrics` の
入力負荷を増やしたくない（続く台帳 > 完璧な台帳）ので迷っています。
